01 The problem: write stalls

LSM-tree key-value stores buffer writes in memory, then flush and compact them to disk in the background. Under heavy write pressure one stage falls behind, a component overflows, and the database stops accepting writes — throughput collapses from hundreds of thousands of ops/sec to near zero. That freeze is a write stall.

02 How ADOC works

Every 1 second ADOC detects which component is overflowing and retunes two knobs — thread count and batch size — using AIMD (the probe-up / back-off-fast idea from TCP). One overflow is handled per window, priority L0O > RDO > MMO.

MMO

Memory Overflow

Active MemTable fills before the previous one flushes — flush can't keep up.

↓ fewer threads · ↑ bigger batch
L0O

Level-0 Overflow

Too many Level-0 files (>20) — L0→L1 compaction lags the flush rate.

↑ more threads · batch unchanged
RDO

Redundancy Overflow

Too many pending-compaction bytes (>64 GB) — deep compaction lags.

↑ more threads · ↓ smaller batch

ADOC's core claim reproduced: write stalls eliminated. Throughput is comparable and noisy on a fast disk; the paper's throughput gains appear most on slower, stall-dominated devices.
